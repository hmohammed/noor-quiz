# UX review — T021 round 1

## Findings
- [must-fix] apps/web/src/features/communities/CommunitiesPage.tsx:250 — The invite UI is a second block after the whole communities page, and `.invite-dialog` is only an in-flow box (`styles.css:403`). Tapping Invite on a phone leaves the person at the community row; the link and QR sit below the create form, with no scroll into view. The section is `role="dialog"` and `aria-modal="true"` (`InviteDialog.tsx:35`) but focus stays on the page, Escape does not close it, and the list and form stay active, so a second tap creates another link and swaps the QR. The dialog title is only "Invite", so two communities cannot be told apart. — Render it over the page (or directly on that row), move focus into it when the link is ready, restore focus on close, close on Escape, and make the rest of the page inert. Show that community’s name with `dir="auto"`.
- [must-fix] apps/web/src/features/invites/JoinPage.tsx:97 — Once the preview is ready, a `loading` session still switches the page to "Loading the invite…" and removes the name and the Join button. That is what happens when a signed-out visitor taps Join: `signIn()` sets the session to loading (`session-context.tsx:151`) while the Google popup is open. If sign-in fails, `sessionKind === 'error'` replaces the preview with `join.error` (`JoinPage.tsx:105`), and Try again only refetches the preview (`JoinPage.tsx:76`), so the button on this page does not try sign-in again. Closing the popup is fine: that path returns to signed-out and shows the name again. — While the preview is ready, keep the community name on screen. During the popup, show the existing "Signing in…" line and disable Join. If sign-in fails, show the name, the sign-in failure, and a Try again that calls `signIn()`.
- [must-fix] apps/web/src/features/invites/JoinPage.tsx:41 — A malformed token is HTTP 400. Only 404 and 410 are handled, so a truncated link (easy to get from a chat app) shows "Something went wrong. Please try again." Retry requests the same token and fails again. — Treat 400 as the not-found state: "This invite link is not valid.", no Join button, no retry.

## Nits (non-blocking)
- apps/web/src/i18n/en.json:92 — "This invite link is not valid." and "This invite link is no longer available." are clear and correctly show no community name and no Join button. A short next step ("Ask the person who invited you for a new link.") would help a visitor who is stuck.
- apps/web/src/features/invites/JoinView.tsx:74 — After "You joined", the only way onward is the header Communities link. A line or link on the page would make that next step obvious. A second accept of a live link correctly uses this same joined state and the name from the accept response. An expired or used-up link stays on `join.gone` for everyone, including someone who is already a member, because the public preview is 410 and has no Join button; a signed-in member can still open Communities in the header.
- apps/web/src/styles.css:420 — Copy, Join, and Close use `.auth__button` (2.75rem). The invite URL link has no minimum block size, so a single-line link is under a 44px touch target.
- apps/web/src/features/invites/InviteDialog.tsx:73 — "Copied" only replaces the button label. A `role="status"` next to it would announce the copy even when the button name change is missed. Copy failure already keeps the link and uses `role="alert"`.
