# UX review — T013c round 3

## Findings
- [must-fix] apps/web/src/features/auth/session-context.tsx:179 — Agreeing on "Before you start" starts the browser-timezone `PATCH /v1/me` with no abort signal (`applyTimezoneDefault` at line 74, called without `signal`). That request is not the `pending` controller `deleteAccount` aborts at line 191, and it does not go through `updateMe`, so the generation check there never runs. `PATCH /v1/me` is `requireUser()` then `requireConsent()` (`apps/api/src/routes/me.ts:58`), and `requireUser()` calls `getOrCreateUser` (`apps/api/src/middleware/require-user.ts:30`). On a slow connection the member can agree, open Profile, and confirm delete before that save finishes. The delete succeeds and the page goes to the signed-out home, then the late save creates a new account for the same Google sign-in. The next sign-in is no longer a blank start, which is the opposite of what the confirm step promised. — Start that timezone save on the same controller `deleteAccount` aborts, and skip sending it when the generation has already moved.

## Nits (non-blocking)
- apps/web/src/features/profile/DeleteAccountView.tsx:22 — Entering `confirming` focuses Cancel. `deleting` then disables that button, so keyboard focus drops to the page. "Deleting…" is only the disabled confirm button's label. The section sets `aria-busy` and has no `role="status"` or `aria-live`, so a screen reader is not told the request is still running. After a failure, focus is not moved to the alert or to Cancel when the buttons are enabled again. Put the deleting label in a `role="status"` element and move focus there; on `error`, move focus to the alert.
- apps/web/src/features/auth/session-context.tsx:197 — If sign-out fails after a successful delete, the promise still resolves and the page goes home, but the banner shows `auth.error` ("Sign-in failed. Please try again.") and a Sign out button (`AuthButtonView.tsx:62`). The account is already gone. Say that it was removed, and that they still need to finish signing out.
- apps/web/src/features/profile/ProfilePage.tsx:141 — A successful delete lands on `/` with the same "Sign in with Google" banner as an ordinary sign-out. The confirm copy has just said the Google account itself is not deleted, so it is easy to think the Noor account is still there. Signing in again does show "Before you start", which only helps on the next visit. A short translated line that this account was removed, and that signing in again starts fresh, would close that.
- apps/web/src/features/profile/ProfilePage.tsx:129 — A profile save that was already in flight is aborted when delete starts, and that rejection sets the form status to `error`. The locked form then shows "Could not save your profile. Please try again." while Save is disabled. Ignore a save that delete cancelled, and leave the form status unchanged.
- apps/web/src/features/layout/AppLayout.tsx:16 — Until the member agrees, the Profile link is hidden and `shouldShowConsentGate` replaces `/profile`, so Delete is unreachable. Sign-in has already created the account. The privacy page, which they can open from that screen, still says "You will be able to delete your account and its data from your profile." (`en.json` `privacy.rights.body`). Point that sentence at the profile control, and give someone who declines a way to delete without agreeing.

## Checked
- Round 1 must-fix still holds for a profile save: once delete leaves `idle`, `ProfilePage.tsx` ignores edits and saves, and `ProfileFormView.tsx` disables the name, language, timezone, and Save controls. `updateMe` shares the abort controller `deleteAccount` cancels before `deleteMe`, and it returns before the PATCH if that generation has already moved.
- Flow for someone who has already agreed: Profile, then "Delete my account", then a confirm step whose first focus is Cancel, then delete and `navigate('/', { replace: true })`. Cancel returns to the intro and sends no DELETE. A failed delete shows `profile.delete.error` in a `role="alert"` and enables Confirm and Cancel again. A second confirm while `deleting` is ignored, and both buttons are disabled. The section sits outside the `<form>`.
- After a successful delete, signing in with the same Google account hits a new user whose consent is required. The shell shows "Before you start" and hides Profile until they agree again (`ConsentGate`, `e2e/delete-account.spec.ts`). The RTL check agrees on that screen first, then opens the confirm step.
- Copy: every new string is `t('profile.delete.*')` in `en.json`. The intro and confirm name the profile, language, timezone, privacy-consent record, and sign-in link, say the Google account itself is not deleted, and the confirm says this can't be undone. No answers or memberships. No state renders a raw key.
- Accessibility: real `type="button"` controls, the section is `aria-labelledby` the `h2`, inputs keep their labels, and `:focus-visible` outlines the delete buttons. New buttons use `min-block-size: 2.75rem` (44px at the default root size).
- RTL: new rules use logical properties and `align-self: start`. The actions row is `flex-wrap` with `gap`. The display-name field still has `dir="auto"`. The delete section does not render the person's name.
- The delete UI does not show quiz answers or explanations.
